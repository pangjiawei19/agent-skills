# 项目结构与架构约定

初始化工程结构、确定模块职责与依赖方向、安排启动组装，或调整公开契约、跨模块依赖或架构检查规则时读取。以清晰职责、可控依赖和可验证行为为目标，目录与组件选择适配实际技术栈。

## 适用条件与产出

适用于服务、前端应用、命令行工具和库。这里的模块指有明确调用接口和内部实现的代码组织单元，可以是函数、包或业务功能集合，不等同于独立服务。

产出包括与当前需求匹配的目录、必要入口及简短的架构约定。已有合理结构时沿用并补齐，不为符合某种目录样式整体重排。

技术栈尚未确定时，可以先形成通用约定；具体源码布局和可执行入口待影响它们的技术决策明确后落实，交付时说明未落地部分。

## 必须满足的要求

### 职责与调用接口

- 每个模块有清楚的职责和对外调用方式，内部实现只暴露调用方确实需要的部分。接口也包括输入、输出、可见副作用及失败方式，不要求使用语言中的 interface 关键字。
- 公开契约拥有调用方需要的数据结构、行为接口及可识别的失败语义，按语义确定归属，具体实现满足契约。可以引用语义合适的稳定基础类型，不统一集中到一个公共契约包；错误标识与协议仍由 [错误处理模块](error-handling.md) 维护，不另建编号或重复定义。
- 业务规则与 HTTP、UI、命令行、消息消费等入口的输入输出处理可区分。涉及独立业务判断时，将其组织为可直接调用和验证的逻辑；简单转发或 CRUD 可以沿用框架惯用写法。
- 调用方通过明确接口使用其他业务模块，避免绕过接口直接修改其内部状态或写入其负责的数据。确需共享查询或跨模块事务时明确所有权与协调位置，数据细则由数据库模块维护。
- 外部服务、数据库和文件等交互集中在职责明确的实现位置。业务调用方应能看出可能的 I/O 和失败方式，避免为了隐藏依赖而把远程操作伪装成无副作用的普通取值。

### 依赖方向

- 业务模块之间保持无循环依赖。出现相互调用需求时，优先重新划分职责、由上层协调，或提取确有共同语义的契约；使用全局查找或服务定位器不能算消除循环。
- 独立业务规则不依赖具体 HTTP 请求、UI 控件或命令行解析对象。由入口转换为规则所需的参数，结果再转换为外部表达。
- 通用技术能力不反向依赖某个业务模块。业务模块可以依赖通用能力；跨业务流程由明确的协调位置负责。
- 配置解析、密钥解析等纯技术逻辑按具体语义归属，避免为了复用函数而借道认证实现、业务客户端或资源组装模块。核对直接及传递依赖，不因函数体纯净就忽略其模块连带引入的运行依赖；业务专属规则仍留在业务模块，共享代码按用途命名，不堆入无边界的通用 utils。
- 模块有真正的替换、隔离测试或兼容需求时，按调用需要在语义拥有者附近定义足够小的契约，由具体实现满足。避免仅为了层次齐全给每个类配一个同名接口。
- 对确需独立的契约，检查公开数据、行为和失败类型的实际来源，类型依赖也不应反向耦合具体实现。语法上仅导入类型不自动证明边界独立；没有隔离需求时可复用合适类型。

这些要求约束模块间依赖，不限制模块内部合理的函数调用。框架约定的发现与注册机制可以使用，但应能追溯到实际实现及配置位置。

### 架构检查的扫描与解析

仅在采用自动架构检查时适用，优先复用已有工具。明确扫描范围、模块边界及例外，按实际语言和构建解析规则识别类型与运行依赖，不能只凭导入字符串猜测归属。声明必需范围为空、无法解析或包含不支持的形式时失败，不静默丢失依赖后报告通过；其他无法静态覆盖的行为说明边界及补充验证。例外限定具体方向、范围及原因，扫描不越过授权边界。

### 启动与资源组装

- 应用入口或框架规定的组装位置负责创建运行依赖、注册功能并启动应用。库暴露初始化方式，由宿主控制生命周期。
- 普通模块的导入不应隐式启动服务、执行迁移或建立外部连接。框架要求的声明式注册可以保留，运行副作用由明确的启动阶段承担。
- 客户端、连接池和后台任务有明确的创建与释放责任。优先使用框架生命周期机制，具体启停行为由 [服务生命周期模块](service-lifecycle.md) 维护。

## 推荐默认值与调整条件

| 事项 | 默认做法 | 需要调整的情况 |
| --- | --- | --- |
| 目录组织 | 优先沿用语言和框架惯例；多个业务能力出现后，将经常一起变化的代码按业务能力组织，模块内部按需分职责 | 单一用途工具或小型库可以平铺；框架有固定入口目录时，保留入口并连接业务模块 |
| 部署单元 | 单个应用从尽可能少的部署单元开始，在进程内组织模块 | 已有独立部署、权限隔离、扩缩容或团队交付需求时再拆分；前后端运行环境不同可以分别构建 |
| 抽象与共享 | 代码先归具体职责；共同语义稳定且有真实使用场景时提取共享能力 | 有明确协议、替换或隔离测试需求时可以提前建立接口，无须等待出现重复实现 |
| 外部依赖替换 | 通过普通参数、构造参数或框架现有机制提供依赖 | 只有手动组装确实难以维护时才考虑额外容器或抽象体系 |
| 数据类型 | 类型放在其语义拥有者附近；简单场景复用合适的类型 | 外部协议、持久化细节、敏感字段或版本兼容要求不同，再分别定义并显式转换 |
| 约束检查 | 先利用语言可见性、模块导出和已有检查工具 | 跨模块误用容易发生且有低成本工具支持时增加自动依赖检查；小工程可先人工审查 |

共享代码按具体用途命名，例如时间处理或某种协议转换。已有 common、utils 目录可以保留，但需明确允许放入的内容，业务规则仍归其所属模块。

DDD、整套六边形架构、CQRS、事件总线、微服务或 monorepo 都是按具体问题选择的方案，不是初始化的必选项。模块拆分不以文件行数、层数或未来可能的规模为唯一依据。

## 实施指引

1. 检查现有布局、框架约定、公开契约及启动入口，确定当前需求下最小的职责与依赖划分。
2. 实现必要结构和入口，复用语言及框架机制。无业务时只确立组织规则，不增加演示业务、空层或尚未需要的检查器。
3. 长期规范记录模块位置、职责与契约归属、允许依赖、新增能力的放置规则及重要例外；采用检查器时声明覆盖边界。复用已有位置，简短规则可内联，确需分册且无现有位置时采用 `docs/agents/project-structure.md`。

本模块明确能力的责任位置，配置、SQL、错误和生命周期契约由对应模块维护；文档及入口遵循 [统一交付要求](../SKILL.md#统一交付要求)。

## 验收标准

- 实际布局符合职责约定，从项目入口可确定新增业务、外部接入及共享逻辑的位置，没有无用层次或占位业务。
- 检查现有跨模块调用与类型来源，无循环依赖或绕过接口；需独立的契约不依赖实现取得。契约迁移同时验证适用协议与数据兼容，类型检查不能单独证明兼容。
- 普通模块导入不启动无关运行资源，资源的创建与释放责任明确；独立业务规则可直接验证，不要求额外启动 UI 或 HTTP。
- 采用架构检查时，从统一入口用合法及违规依赖验证实际解析、例外和失败传播；覆盖声明范围，缺失解析与空扫描不能伪报成功。静态不能覆盖的行为明确说明或补充验证。
- 有工具链时运行适用构建、类型及启动／加载检查；无代码或条件时说明不适用或未验证，不伪造成功。

遵循 [测试政策](testing.md#测试政策)，区分结构审查、实际运行和后续开发是否遵守规范。
