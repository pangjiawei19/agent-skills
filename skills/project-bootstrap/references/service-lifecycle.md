# 服务运行与生命周期

建立或补齐健康与就绪检查、启动组装、退出协调，或调整后台工作及资源启停时读取。新建常驻 HTTP 服务默认提供 `GET /health` 和 `GET /ready`，已有工程保留有效路径；探针、初始化、工作接入和资源释放接入同一套生命周期。

## 适用条件与产出

适用于常驻服务，以及持有连接、调度器或其他运行资源的工作进程。HTTP 服务接入适用探针；后台进程沿用运行平台支持的状态检查，不为使用本模块额外启动 HTTP 服务。静态前端与库无需独立健康服务，库由宿主控制生命周期；一次性任务和初始化脚本落实适用的清理及退出语义。

产出包括实际启停入口、适用探针、必要的工作跟踪与资源释放、运行说明及验证结果。复用框架生命周期和简单的启动组装，按实际依赖安排执行顺序，不默认建设通用生命周期框架。已有有效实现局部补齐，探针路径与接口兼容要求保留。

## 健康与就绪检查

| 检查 | 默认语义 |
| --- | --- |
| `GET /health` | 轻量检查进程及应用的基础响应能力，正常返回 200；外部依赖暂时故障不直接使存活检查失败 |
| `GET /ready` | 已完成必要初始化、关键运行依赖可用且未进入关闭阶段时返回 200，否则返回 503 |
| Startup Probe | 初始化较慢或运行平台需要时按实际启动条件接入，不统一增加第三个 HTTP 入口 |

- 先明确哪些依赖是全服务接收业务的必要条件，哪些仅影响部分功能。可选功能故障按明确策略降级，不机械地将所有外部服务都列为就绪前提；若整项服务不可用，应如实体现就绪失败。
- 就绪依据启动与关闭状态，以及关键依赖的轻量、有超时检查。按需短期缓存或合并并发探测，明确有效期和超时；关闭状态立即覆盖旧的成功结果。实际依赖故障及恢复应能反映到就绪结果，固定返回成功不算接通。
- 探针等待超时不代表底层操作已停止。跟踪未结束的借连接、请求或其他检查，按实际客户端能力取消、合并或限制在途数量，避免后续探针不断叠加；迟到获得的资源仍需释放，迟到成功不能恢复关闭中的就绪状态。
- 探针只返回必要的运维状态和安全原因，不套用业务 REST 响应包裹或错误码协议，不暴露凭据、配置及完整内部异常。默认无需业务认证，由部署环境限制访问范围；已有平台认证要求适配其访问方式。
- 端口监听成功不等于业务已经就绪。允许初始化期间先开放探针，但业务入口仅在必要条件满足后接入；进入关闭阶段后保留适用探针响应，同时停止接收新业务。

## 启动与失败处理

- 在连接资源、监听或启动任务前完成 [配置模块的启动校验](configuration.md#统一加载与启动校验)。随后初始化必要资源和功能，满足条件后接收业务；调度、消费及轮询也要等待其前置条件完成。
- 必要前提采用轻量只读检查。应用自有 Schema 的创建及升级遵循 [数据库模块](database.md#schema-脚本与独立初始化)，放在独立入口，不混入主程序启动。
- 永久性配置、必要文件或 Schema 错误清理已获得资源并以非零状态退出。必要依赖的临时故障可有限重试，遵守 [错误处理模块的调用策略](error-handling.md#超时取消与重试)，限定总启动预算；耗尽预算仍失败，不无限等待或仅记录错误后宣布就绪。
- 服务运行期间的关键依赖故障使就绪失败，恢复后重新就绪；不因普通外部故障立即退出进程。可选能力启动或运行失败的继续条件和降级状态明确，不把静默忽略等同于允许降级。
- 生命周期保护覆盖初始化全过程。获得资源后立即登记释放责任，初始化中途失败、端口绑定失败或收到退出信号时，清理当前已获得资源。关闭开始后，尚未完成的初始化不能再接入新工作；迟到获得的资源也要释放。
- 一次性任务正常完成后清理并以零状态退出，执行或必要清理失败时返回非零。清理统一执行一次，保留执行失败与清理失败各自的原因，避免在成功与失败分支重复调用清理。

## 退出协调与资源顺序

- 进程有明确的关闭协调者，统一处理 `SIGTERM`、`SIGINT` 及程序化退出，复用框架释放能力。关闭幂等，框架与业务不争夺最终退出权；库由宿主控制退出。
- 各阶段共享一个关闭总预算，并与运行平台终止宽限期配合。正常清理不提前强退；预算耗尽后执行明确的最终退出策略，不能仅设置退出码后无限挂起。

关闭按实际依赖执行：

1. 标记未就绪并停止新业务、调度及消费。应用自身实施接入保护，早于昂贵正文处理，实际接纳与关闭状态协调，不能仅依赖平台摘流。
2. 按执行契约等待在途工作完成，或取消并等待结束确认。关闭竞争时让调用方得到正确拒绝或中止结果，未执行的工作不能伪装成功；已开始响应按原协议处理。
3. 完成必要状态写入、挂起或失败标记，再释放依赖资源；只并行清理相互独立的资源。按 [安全策略](security.md#资源限制与执行隔离) 保留停止已有工作的控制能力，直至相关工作结束或总预算耗尽，并协调已接纳控制操作。
4. 在最后使用后按 [指标关闭契约](metrics.md#注册器与采集器的关闭契约)、[追踪要求](metrics.md#链路追踪) 和 [日志要求](logging.md#输出故障与生命周期) 完成观测资源的刷新、关闭，汇总结果后退出。

每项清理失败后继续可独立执行的步骤，收集同步、异步及并行失败。原始操作与清理错误分别保留，诊断失败不阻断清理。正常结束且必要清理完成时返回零；必要清理失败、未完成工作无法按契约处理或预算耗尽时返回非零，可选遥测失败按明确策略告警。不可恢复的进程异常停止接入、有界清理并非零退出，由宿主负责重启。

## 后台工作与资源所有权

- 每项后台活动及资源有明确所有者、停止入口和释放责任，包括首次工作后才创建的资源。共享资源只由所有者或合法接管者处理，独占资源才可整体清理。
- 工作从登记、异步初始化到运行均纳入协调；取消早于执行器就绪时仍须保留并在启动前生效。关闭或取消后的迟到初始化不能重新启动工作，已取得资源按当前归属释放一次。
- 分别判断停止等待、取消被接纳、底层执行结束及远端副作用。HTTP 或订阅结束不代表独立后台工作结束；未结束操作仍由所有者跟踪，迟到结果不改写终态，无法确认的远端结果如实报告。SQL 与连接状态遵循 [数据库模块](database.md#sql-访问索引与连接)。
- 采用 [执行容量限制](security.md#资源限制与执行隔离) 时，原子预留与工作登记纳入同一接纳过程。确认未启动或实际结束后归还本次名额一次；取消失败或结果未知时不能提前释放，旧执行的清理不能影响新执行。
- 任务恢复、重试及挂起遵循业务契约，多实例仅处理自己拥有或合法接管的工作。使用 SDK 时核对其真实取消及释放能力，不以方法名称或调用返回判断资源已结束。

## 实施指引

1. 盘点运行类型、必要与可选依赖、框架生命周期和资源所有者，确定实际启停及状态入口。
2. 接通探针、启动失败清理和统一退出，按实际工作契约确定接纳、取消、恢复及预算耗尽策略，复用框架能力。
3. 长期规范记录入口、探针与降级语义、资源顺序、工作归属、预算及退出策略；按 [交付模块](build-delivery.md#外部部署交接) 交接平台探针、摘流及宽限期，不执行部署。

## 验收标准

按 [测试政策](testing.md#测试政策) 使用隔离资源。涉及运行行为时通过实际启动入口与真实进程验证，保留待验 SDK 路径；下游可用确定性替身，无须真实付费调用。

- 探针反映启动、必要依赖故障与恢复、降级及关闭；超时后底层探测不无限叠加，迟到成功不恢复关闭状态。
- 初始化失败或中途退出后不再接入工作，已取得及迟到资源被正确释放；一次性入口的成功、执行失败及清理失败产生正确退出状态。
- 完成首次实际工作后验证信号、在途排空、末尾输出与最终退出；存在容器或包装入口时确认信号真正到达应用。
- 新增或修改异步接纳、取消或容量机制时，受控触发启动交接和结束竞争，检查执行效果、协议结果、名额及资源归属。未接纳工作不执行、不伪报成功，既有控制操作按契约保持可达。
- 清理及日志故障不阻断剩余独立清理，原始错误可定位，退出有界且状态准确。测试工具超时强杀只能作为兜底，不能证明应用已按期退出。
- 多实例或共享资源适用时验证不误改其他所有者的数据；与日志、指标组合时核对最后使用和释放顺序，同一次链路可验证各模块结果。平台行为与应用验证分别报告。
