# 开发环境与依赖管理

初始化工具链、依赖管理及本地运行方式，或补齐工程首次运行说明时读取。目标是由 Agent 尽量自动准备环境、安装依赖并实际验证运行，只留下必要的人工步骤，使使用者能够通过明确入口重复启动工程。

## 适用条件与产出

适用于有运行、构建或开发工具依赖的工程。复用已有清单、版本约定和命令；纯文档工程只配置实际需要的工具。

产出是适用的工具链声明、依赖清单及解析结果记录、本地服务配置、准备与启停及检查入口，以及实际验证结果。技术栈尚未确定时，只整理已知前提并澄清影响安装的选择，不生成虚构清单或为选型方便先安装一套工具。

## 必须满足的要求

### 工具链与环境前提

- 声明实际需要的语言运行时、构建工具和包管理器的版本约束。区分项目支持范围与已验证的开发基准，避免将“支持某范围”描述为所有版本均已验证。
- 使用技术栈认可的项目级版本声明、工具包装器或等价机制。相同信息优先维护一份；其他工具需要重复声明时保持一致，文档指向其来源。
- 按实际工具版本核对配置来源及生效方式。新增或调整关键策略时，用合法及违规样例验证；存在歧义时再做隔离对照，不放宽正式策略。
- 说明必需的系统依赖、操作系统或架构限制，以及私有依赖访问前提。仅记录影响当前工程的条件，不扩展为全平台支持承诺。
- 项目依赖安装在项目环境或工具管理的隔离环境中。确需全局安装的运行时或系统工具作为明确前提处理，避免改动其他工程依赖的配置。
- Agent 自动完成已授权范围内的项目配置、依赖安装和本地服务准备。安装 Docker 或系统组件、获取凭据前先检查现有条件；确需人工完成的步骤集中说明，条件具备后继续自动准备和验证。

### 依赖声明与可重复安装

- 工程直接使用的依赖显式声明，并按生态机制区分运行、构建、测试及可选依赖。不要依赖其他包偶然带入的传递依赖。
- 应用采用生态支持的锁文件、固定解析版本或等价机制记录依赖结果；必要文件纳入版本管理。没有原生锁文件的工具使用其支持的版本约束和解析方式，不手写虚假的锁文件格式。
- 可复用库区分开发环境的依赖固定与对使用者公布的兼容范围，不能为了复现开发环境而无依据地收窄消费者的版本选择。
- 安装已确定依赖与主动升级依赖分开。提供校验清单与锁定结果一致、且不隐式更新依赖结果的安装方式；工具无法一步完成时组合相应检查。
- 实际运行、构建和测试仍遵守锁定结果；允许声明的准备步骤，但需核对隐式安装、重新解析及布局参数的兼容性。生产打包与最终依赖按 [交付模块](build-delivery.md#构建与运行产物) 验收。
- 锁文件由对应工具生成。依赖变化时同步更新清单和解析结果，并验证受影响行为；不把删除锁文件后重新解析全部依赖作为常规故障修复。
- 必需的仓库、索引和解析选项以项目可复现的方式提供。凭据通过现有认证机制注入，配置及示例不包含真实令牌；不自行替换团队仓库或关闭证书校验。
- 安装脚本许可及依赖安全检查遵循 [安全模块](security.md#依赖安装脚本与安全检查)，结合实际包管理器落实，不把锁定安装当作安装过程的安全证明。

“可重复安装”指在已声明的工具链和平台条件下解析到受约束的依赖结果，不等同于跨平台字节一致构建、永久可下载或完全离线安装。

### 本地运行与外部依赖

- 明确从首次检出到可运行的顺序：准备工具、安装依赖、提供必要配置、准备外部服务、启动并检查。无须为每一步另建脚本。
- 依赖服务默认在开发者本地通过 Docker Compose 运行，应用默认在宿主机运行。按需生成 Compose 配置，说明服务版本、端口、连接参数、持久化位置和启停入口；不需要外部服务的工程不引入 Compose。
- 启动与检查使用项目提供的命令入口，说明工作目录及必要参数。库以构建、加载或测试作为运行入口，不强制增加服务进程。
- 有本地包依赖时，接通首次构建、持续编译及消费端更新。编译失败阻止失败的新产物传播，明确是否沿用上次成功产物；更新和恢复通过实际消费者验证，旧响应不作为新代码生效证据。
- 开发包装器和监听器优先使用工具公开能力，明确失败传播、停止责任及限制，不默认自建进程管理器。开发重载与 [生产排空](service-lifecycle.md#退出协调与资源顺序) 分别验证，进程清理遵循 [资源归属](testing.md#隔离环境数据与清理)。
- 数据库、缓存等外部服务只在实际需要时准备。已有可用的本地服务允许复用，核对类型、版本及连接配置，避免重复启动与端口冲突；替代实现存在语义差异时记录限制，不把替代环境当作真实接入验证。
- 初始化与重置数据分开，默认操作可重复执行且保留已有开发数据。涉及删除数据的命令明确用途，不混入普通安装、启动或检查过程。
- 重复准备环境时保留已有本地配置，只补充实际缺项；配置冲突明确处理，不用重新复制示例文件覆盖使用者的值。
- 开发资源使用与生产隔离的配置、凭据及数据位置。自动准备的临时进程和资源有明确的停止或清理方式，结束验证时清理本次创建的临时资源。
- 开发与测试资源隔离，明确停止、重建和重置的数据保留策略；新增或修改存储配置时用专用实例及合成数据验证，只清理本次拥有的资源，遵循 [测试隔离要求](testing.md#隔离环境数据与清理)。
- 本地缓存、虚拟环境、构建产物和带密钥的配置按生态惯例排除出版本管理；需要追踪的清单、锁文件和无敏感信息的示例保留。

## 推荐默认值与调整条件

| 事项 | 默认做法 | 调整条件 |
| --- | --- | --- |
| 工具选择 | 沿用已有工具；新工程选择与框架兼容、受维护的稳定版本，并记录工具链版本 | 有团队规定或明确能力缺口时调整，不在同一依赖单元混用多个包管理器 |
| 版本记录 | 记录已验证的开发基准，版本选择检查当前支持状态 | 对外发布库需要表达支持范围；多平台存在差异时记录各自条件 |
| 本地入口 | 复用包管理器、构建工具和框架命令 | 有稳定且容易遗漏的多步操作时再封装轻量脚本；不为统一命令名引入额外任务系统 |
| 本地运行 | 依赖服务用 Docker Compose，应用在宿主机运行 | 允许复用可用的本地服务；库和纯文档工程按实际需求省略服务进程 |
| 完整开发环境封装 | 不默认将应用及全部开发工具放入容器 | 用户明确要求或已有工程采用 Dev Container 等方案时适配 |
| 安装模式 | 日常校验和后续 CI 使用受约束的安装路径 | 明确新增或升级依赖时使用更新流程，并审查解析结果变化 |

不要求所有项目离线构建、使用同一包管理器或自动升级至最新版本。多语言工程可以分别管理依赖，但应明确各自入口和相互前提。

## 实施指引

1. 检查清单、版本、锁定结果、已有命令与服务，定位实际生效配置和缺项；集中说明需要人工处理的系统条件或凭据。
2. 补齐当前所需配置并按锁定结果安装，准备 Compose 或复用本地依赖；实际走通应用或库入口，不顺手升级或重建用户环境。
3. 长期开发规范记录工具与依赖约定、首次运行顺序、适用本地包更新及数据保留策略，链接实际命令；复用现有位置，无合适文档时采用 `docs/development.md` 并接入项目入口。

## 验收标准

按本次改动选择检查，使用隔离副本或专用资源，不清空用户环境模拟首次安装。

### 重点场景与验证层级

| 范围 | 预期结果及验证方式 |
| --- | --- |
| 工具与安装 | 实际版本符合声明，从受约束安装走通所需命令，重复安装不无故更新锁定结果；新策略的违规样例产生预期失败 |
| 运行与依赖 | 实际应用或库可运行，必需依赖连接成功；容器运行、配置生成和替身通过分别说明证据边界 |
| 本地包与包装入口 | 本次涉及更新或包装机制时，从真实消费者验证修改、编译失败及恢复，并确认失败和停止结果准确、无遗留活动 |
| 重复准备与数据 | 保留已有配置和开发数据，不重复创建服务；变更的停止、重建及重置行为符合声明，开发与测试不互相误清 |
| 版本管理 | 必需清单、锁定结果和安全示例可追踪，敏感配置与本地生成物被排除，无无关环境改动 |

未验证首次安装、实际依赖或运行行为时明确报告；缺少网络、权限或凭据时说明恢复步骤，不通过反复安装或升级掩盖问题。无业务代码时验证已有骨架，不制造业务或空成功命令。
