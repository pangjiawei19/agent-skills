# AI 协作与工程文档

在新工程中建立 AI 工作约定、为初始化工程补齐约定，或从已有工程文档提炼长期协作规范时读取。目标是让后续 Agent 找到项目要求、采取符合约定的行动，并能验证自己的修改。

## 适用条件与产出

适用于使用 AI 参与开发的工程。已有约定时补充缺项，保留仍适用的项目规则和人工内容；依据已确认约定修正规则冲突，需要新决策时才向使用者澄清。

产出包括：

- 根目录 `AGENTS.md`：通用工作约定、必要的项目入口和带触发条件的规范索引。
- `docs/agents/meta-conventions.md`：规范的编写和维护要求。已有等价文档时复用原路径。
- 项目已有或其他模块实际沉淀的长期规范链接，包含复用且未修改的有效文档；仅在有内容时建立分册。

产出必须在目标工程中自包含，不依赖安装本 skill 的本地路径或原参考工程。

## 文档生命周期与权威位置

- 阶段性开发文档承载探索、方案比较、暂定方案、进展和待办；长期协作规范承载已确定的约束、适用条件、操作要求和验证方式。按内容与维护用途判断生命周期，不以文件名或所在目录直接判定。
- 长期规范及其必读引用须能独立指导工作，不直接或通过其他说明间接依赖可能归档、删除的开发文档，也不依赖会话中的隐含信息。开发文档可以反向引用长期规范；来源追溯不能承载执行所需的唯一说明。
- 根 AGENTS.md 是通用约定与按需规范索引的统一入口，详细规则复用项目已有合理位置。各项具体规则明确唯一维护位置，入口摘要与细则保持一致，不强制按 skill 模块逐份建文档。
- 提炼后默认保留原开发文档，在其现有入口或相关内容处说明阶段资料定位及对应长期规范的权威位置；只按当前范围修正失效引用。归档、删除及实现差异修复按当前任务范围处理，不因整理规范自动扩展。

## 已有内容的分类与核对

盘点时逐项区分以下内容，作为提炼依据，不要求目标工程额外维护固定格式的分类表：

| 内容 | 提炼方式 |
| --- | --- |
| 长期要求 | 依据已确认决策保留适用条件、操作、例外和验证方式，迁入或更新权威位置 |
| 当前实现 | 对照代码、配置及测试核对事实，链接实际入口；现状本身不构成正确规则 |
| 暂定方案 | 保留暂定性质与待确认边界，不因迁移变为已确认契约或强制规则 |
| 实现缺口 | 区分已确认目标与实际状态，标明尚未实现或未验证范围，不将文档目标写成已完成能力 |
| 历史记录 | 留在阶段资料或历史说明中，不作为当前操作的必需前置 |

配置和测试是核对实现及证据范围的依据，文件存在、测试使用替身或跳过不能证明能力已接通。发现规范与实现不一致时记录差异，依据已确认约定修正文档；缺少决策依据时保留待决事项，不擅自选择“代码优先”或“旧文档优先”。

## AGENTS.md 应包含的要求

以下要求是生成时的内容依据，应结合项目组织成简短入口，不需要照搬本文件的说明文字。

### 工作范围与实现方式

- 以当前任务和适用的项目约定确定修改范围。需求文档存在时按需读取，不假定项目必须有 `spec.md`。
- 修改前阅读适用规范、目标实现及受影响的调用方或接口；改动范围应足以解决问题，避免夹带无关重构。
- 优先利用已有抽象和依赖；新增抽象或依赖应有当前需求依据。
- 同一业务概念沿用项目已确定的术语。不同语言的命名风格、外部接口和兼容性要求可以保留差异，必要时记录映射。
- 修改后审查差异并执行适用检查，交付时说明结果及未验证部分。

项目约定适用于对应工程范围，不宣称高于系统、开发者或用户当前的明确指令。

### 工作区与分支

Git 工程在修改前检查当前分支和工作区变更，保留已有工作。遵循用户明确指定的工作位置及项目分支策略；切换分支前检查是否会影响未提交内容。

已有合适工作分支时继续使用。没有明确分支策略时，不凭分支名假定存在 `develop`，也不把 `release/*` 一律当作开发分支。若当前分支不允许直接开发，按已有策略创建工作分支；缺少会影响实施的信息时再澄清。非 Git 工程跳过分支要求。

### 沟通与文档语言

默认使用中文沟通和编写面向人的文档、说明性注释，使用全角标点。用户明确指定其他语言或已有项目约定时按对应要求处理；代码语法、命令和标识符保留原格式。

提交信息沿用工程已有约定，不预设英文或 Conventional Commits。解释修改时说明行为、原因和验证结果；图示按表达需要使用。

### 检查与测试入口

列出与当前工程匹配的常用启动、构建和检查入口，包括必要的工作目录及前提。以工程实际脚本或配置为准，避免复制容易漂移的长命令。

空工程尚无可执行命令时省略命令章节，并在交付说明中记录这一现状；待实际构建或开发环境建立后再补齐，不编造命令或保留填空提示。

AGENTS.md 保留测试政策摘要：新工程按行为和风险选择验证，可复现 Bug 优先回归测试，核心及高风险行为优先测试先行，已有明确政策保留；交付说明真实接入与替身验证的边界。

完整政策统一维护在 [测试模块](testing.md#测试政策)。选择验证方式、修复 Bug 或调整测试执行前读取适用要求；目标工程已有完整测试规范时沿用并链接，只接入本模块时保留必要摘要。测试规范实际形成后，由入口按条件引用，不在 AGENTS.md 重复维护全部细则。

### 按需读取的规范索引

索引中每个条目同时写明可解析的文档链接和读取条件。例如：

```markdown
- [规范维护](docs/agents/meta-conventions.md)：新增或修改协作入口、长期规范，或整理开发文档中的规则前读取。
```

其他模块条目只在对应文件存在时添加，触发条件应覆盖该规范实际约束的后续新增与修改操作。日志、SQL、指标等详细要求各自维护，通过索引连接；仅列出实现文件或本次变更说明，不能代替相应的长期规范入口。

关键通用约定直接写在入口，必要摘要与分册细则保持一致；仅特定操作需要的内容放入分册。不依赖所有 Agent 都会解释某种 `@` 导入语法，也不在入口自动展开全部分册。

## 实施指引

1. 盘点适用指令、工具入口及现有文档，按前述分类核对已确认决策与实现事实，保留迁移对照依据。
2. 将长期规则整理到已有权威位置，简短通则放入 AGENTS.md，详细规则按需引用；不额外创建 constitution.md，已有有效组织保留。阶段资料保留并标明长期规则入口，暂定项和实现差异维持原状态。
3. 更新 AGENTS.md、README 等发现入口和受影响引用，按 [规范维护资源](../assets/ai-collaboration/meta-conventions.md) 建立项目维护约定。工具专用入口保留独有内容，通过已确认支持的机制连接统一入口，不形成递归加载。

## 验收标准

### 结构与入口检查

- 链接、锚点、配置及命令可定位且符合实际前提，没有安装路径依赖、占位内容或自动导入循环；普通双向导航不视为循环加载。
- 索引有实际读取条件，已有人工及工具专用内容保留，再次执行不会追加同义条目。

### 内容与自包含审查

- 对照迁移前盘点核对有效规则无遗漏，摘要、细则及例外一致，暂定方案不升级为强制规则，实现缺口不冒充完成；冲突按已确认决策处理，缺少依据时标明待决。
- 阅读时排除阶段性文档，仍能从项目入口确定修改代码或规范的规则、实现位置及验证方式；不依赖“沿用此前方案”等隐含上下文，无须删除源文件验收。
- 按 [统一交付要求](../SKILL.md#统一交付要求) 分别报告结构、内容与实际行为结果。链接有效不证明运行能力接通，也不证明后续 Agent 已实际遵守规则；文档整理不新增空测试或触发发布。
