# project-bootstrap 设计

本文面向 skill 维护者，记录当前设计原则、关键决策及演进依据。执行要求以 [SKILL.md](SKILL.md) 和正式分册为准；初始化目标工程时无须读取本文。

当前十三个模块已完成规范编写并接入入口，配有必要模板及辅助脚本。规范与资源完成不代表目标工程能力已接通；真实工程中的整体效果、重复执行与精简前后对照仍待验证。

## 定位与范围

为新工程或初始化阶段的工程沉淀团队共性要求，由 Agent 根据语言、框架、现有能力与运行环境完成适配，减少重复搭建和遗漏。

统一交付包括项目长期规范、必要实现、发现入口和验证结果，具体要求维护在 [统一交付要求](SKILL.md#统一交付要求)。已有实现符合要求时可以只补规范；尚无运行场景时可以先沉淀已确定规则，并说明实现与验证状态。

当前范围不默认包含业务功能、成熟工程全面改造、技术栈迁移、全语言组件目录或独立 CLI。缓存、消息队列、定时任务、对象存储、多租户等仍是按实际需求讨论的扩展候选，不预建空规范或设施。

构建交付形成产物和外部部署交接，代码仓库不执行部署、回滚或生产 SQL。搭建模板本身不授权真实推送、消息通知、云资源创建或生产变更，外部操作遵循用户授权范围。

## 稳定设计原则

1. **要求先于实现。** 先定义行为和结果，再适配技术栈；复用已有有效能力，确需选型时采用成熟方案，不把参考工程的业务特例或组件选择推广为通用标准。
2. **保留团队约定，明确适用性。** 区分必须约束、推荐默认值和项目可选项。日志字段、指标命名、配置语义及已确定基础设施等协作约定保留；模块按需采用，实施顺序由实际依赖决定。
3. **长期规范是正式产出。** 规则应能指导后续修改，不能只介绍现状或记录本次变更。复用目标工程文档位置，简短约定内联，详细内容按需组织，不要求每模块新建文件或接入完整 AI 协作体系。
4. **项目产出自包含。** 后续开发不依赖再次加载 skill，也不直接或间接依赖可能归档的阶段资料。实现及必要依赖位于目标工程或由项目依赖机制提供，不依赖 skill 安装路径。
5. **规则有唯一维护位置。** 跨模块要求通过引用衔接，配置与脚本可直接表达的事实链接其来源。入口提供摘要和读取条件，设计文档解释取舍，避免多处维护完整规则。
6. **变更有范围，重复执行补差异。** 保留有效约定和人工内容，不因整理规范顺带改造所有历史问题。区分长期要求、当前实现、暂定方案、实现缺口和历史记录，不把现状自动升级为规则或将目标描述为已实现。
7. **按风险验收可观察结果。** 规范完整性与实现行为分别检查；专项机制只在实际采用且本次涉及接入或修改时展开。多模块共用代表性链路验证，避免重复维护要求、实施步骤和场景矩阵。
8. **证据对应实际范围。** 文件存在、链接有效、替身通过、真实运行及平台接通是不同证据。保留失败和未验证项；输入变化后重跑受影响检查，不以补写身份或一次复验覆盖旧失败。

| [配置与密钥管理](references/configuration.md) | 文件为主、环境变量显式映射，按公共默认、环境、个人、映射环境变量逐层覆盖，进程值优先于 `.env`。对象按字段合并、数组替换，缺失才继承，空串、`false`、`0` 按实际输入校验；加载前确定引导范围，连接前完成校验。密钥按用途独立初始化并保护已有内容，默认重启生效。 |
| [错误处理与 REST 接口约定](references/error-handling.md) | REST 响应结构按工程商定，错误码工程内唯一登记、按模块划分命名空间，数字为新工程默认，已有字符串协议保留；内部错误不全部编号，MCP 等专门协议单独处理。调用策略围绕幂等、总预算和责任归属，结果未知不自动重发。 |
| [日志与请求上下文](references/logging.md) | 生产默认 JSON 标准输出、info 级别，统一核心字段与安全诊断。服务端建立可信 requestId，后台执行使用独立 executionId；记录责任避免逐层重复堆栈。普通日志故障不改变业务结果或中断清理，强制审计按其契约处理；不固定日志库。 |
| [数据库与 SQL](references/database.md) | 关系型数据库采用根目录 `sql/` 加 DBA 流程，应用启动不建表，本地和 CI 测试库通过独立入口初始化。基线按共享／生产实际使用冻结，不以 Git 提交作为依据。新建或调整结构不新增外键，关联完整性由业务维护；保留单数 snake_case、索引命名、明确主键、默认自增整数及稳定业务标识例外、UTC 时间点和中文注释等约定，不默认引入迁移框架。 |
| [服务运行与生命周期](references/service-lifecycle.md) | 新建常驻 HTTP 服务默认提供 `/health` 与 `/ready`：存活检查不随外部依赖暂时故障失败，就绪检查反映必要初始化、依赖及关闭状态。启动与退出统一协调，关闭使用总预算、明确资源所有者；取消请求、停止等待和实际结束分开，库保留宿主退出权，不另造通用框架。 |
| [指标与可观测性](references/metrics.md) | 新建常驻后端默认随进程启用 Prometheus 拉取与 `/metrics`，基础 HTTP 名称及类型统一，标签有限且路由模板化。零、缺失、无流量和禁用分别解释；Histogram 按整条支持链选择。面板、告警、追踪和采集平台按需接入，应用输出与平台接通分别验收。 |
| [测试与验证](references/testing.md) | 测试由行为和风险驱动，不统一强制 TDD 或覆盖率百分比。分组按需，快速检查默认不依赖外网或真实凭据；必需检查缺条件、空组或全跳过不能报通过。核对状态及资源归属、替身覆盖边界和实际产物，默认关闭重试，避免空测试或强杀掩盖真实问题。 |
| [构建、交付与部署](references/build-delivery.md) | 新建常驻后端默认 Docker 镜像，GitLab CI 验证、推送 AWS ECR 并发飞书通知。默认 MR、develop 与 release/* 执行验证，仅受保护 release/* 的 push 在检查通过后发布镜像。使用不可覆写版本及可追溯产物身份，部分失败和未知结果如实表达；通知失败不重建镜像，镜像推送不称为上线，部署留给外部平台。 |
| [安全基础](references/security.md) | REST 业务接口默认受保护，公开入口显式声明，认证与资源授权覆盖实际执行边界；探针和指标遵循所属模块的运维访问规则。撤权和缓存窗口明确。依输入、外部访问、资源容量及供应链风险接入必要控制，不预置安全产品或分布式设施。秘密泄露及确认影响的高严重问题按有效例外政策阻断；扫描对象与当前输入、产物必须匹配。 |

### 跨模块职责

- **文档与入口：** AI 协作负责规范提炼与维护方法，功能模块负责本领域规则；统一交付要求由入口维护，单独功能模块也需交付适用的长期规范。
- **检查与交付：** 代码质量负责检查规则，测试负责通用验证政策，功能模块负责行为断言，交付负责 CI 门槛和产物交接；安全负责安全门槛政策，扫描身份关联由交付落实。
- **配置与数据：** 配置负责加载、校验和秘密注入；数据库负责数据所有权、Schema 与事务。CI 可准备已确认归属的隔离测试库，不因此获得主程序建表或生产 SQL 执行许可。
- **运行与观测：** 生命周期统一负责工作接纳、取消、实际结束、迟到资源和退出顺序；错误模块负责调用语义，日志负责记录与上下文，指标负责统计口径。各模块引用通用约束，保留自身结果的验收。
- **应用与平台：** 仓库交付运行前提和产物记录；外部平台负责实际部署、摘流、配置注入、采集访问及发布后验收。应用侧通过不代表平台侧完成。

## 模块结构与维护方式

### 资源分工

| 位置 | 维护内容 |
| --- | --- |
| [SKILL.md](SKILL.md) | 唯一可执行模块清单、读取条件、通用流程和统一交付要求。 |

| `assets/` | 复制或适配到目标工程的模板及辅助脚本；具体复制清单由所属模块维护。 |
| [agents/openai.yaml](agents/openai.yaml) | 界面名称、简述和使用提示，与实际能力范围一致。 |

| DESIGN.md | 稳定设计、关键取舍、维护步骤和简要演进依据。 |

不再单独维护完整目录树；资源存在性、复制清单和脚本本地间接依赖一起核对，避免骨架与实际资源再次漂移。确定性的公共工具确有需要时再增加 `scripts/`，不预建空目录。

### 模块内容与反馈处理

模块围绕适用条件、规范与要求、实施指引、验收标准组织，篇幅依复杂度调整。规范区分必须、默认和可选，实施指引只补接入顺序，验收以可观察结果为准，不逐段复述要求。

建设新模块时，先讨论目标、关键取舍与新增团队约定；已有授权覆盖的整理直接执行。此协作方式不要求初始化目标工程时逐项重问已有决策，常规适配由 Agent 完成。

从参考工程提取时，先理解问题及场景，再区分团队共性、业务特例、技术栈机制和历史遗留。参考工程之间的差异应解释原因，据此保留选择条件，而非直接复制一套实现。

收到反馈后先判断属于通用原则、团队约定、实现缺陷还是回归案例。优先修订原规则、修复实现或补有价值的回归；只有独立且普遍适用的新要求才扩充规范。专项 SDK、进程机制、工具参数和穷举故障案例不自动上升为通用设计，也不为缩短正文另拆必读文件。

### 接入与修改步骤

1. 核对当前入口及相关分册，明确本次适用范围、已有决策和唯一维护位置；新增模块再形成对应分册。
2. 更新必要规则与实施指引。仅在确有复用价值时增加模板或脚本，明确适用上下文及依赖，不将示例设为唯一实现。
3. 同步入口的读取条件；能力范围变化时更新描述与界面简述。检查跨模块规则及例外，保留有效旧入口或修正其引用。
4. 核对链接、资源复制清单及本地间接依赖，确保工程产出自包含；执行结构检查与受影响的资源回归，按需取得真实工程证据。
5. 分别报告规范、实现和外部验证状态。设计记录只更新影响后续维护的决策或证据边界，不逐轮追加完整反馈表和重复检查日志。

新增模块通常不需要改写通用执行流程，只有实际依赖或交付方式无法被支持时才调整。

2. **规范迁移：** 用真实混合文档验证有效约定、暂定状态、实现缺口和例外均被正确保留；排除阶段资料后完成代表性任务，区分静态走查与实际 Agent 执行效果。
3. **受影响行为及组合：** 按正式分册和工程风险选择真实入口、SDK、驱动、运行时与产物验证，重点核对初始化、授权、取消与结束、资源归属、未知数据结果，以及错误、日志、指标和关闭的一致性，不要求每个工程展开全部专项场景。
4. **工具和平台接通：** 验证实际工具策略、检查发现与失败传播、生产依赖和产物、真实扫描对象及 CI 权限；在授权条件下取得镜像仓库、通知、采集和部署交接证据，分别报告应用与平台状态。
