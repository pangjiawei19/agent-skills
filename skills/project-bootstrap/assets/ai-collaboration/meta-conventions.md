# 规范维护

新增或修改协作入口、长期规范，或整理开发文档中的规则前读取。本文用于目标工程；采用其他规范目录时，应同步调整本文和入口索引中的位置说明。

## 文档生命周期

- 阶段性开发文档保留探索、方案比较、暂定方案、进展和待办；长期规范维护已确定的约束、适用条件、操作要求和验证方式。按内容和维护用途判断，不仅依据文件名或目录。
- 长期规范及其必读引用独立承载工作所需信息，不直接或间接依赖可能归档或删除的开发文档，也不依赖会话中的隐含信息。来源追溯不能成为必需上下文的唯一位置；开发文档可以反向引用长期规范。
- 整理后默认保留原开发文档，补充阶段资料定位和长期规范的权威入口说明；归档或删除按当前任务范围另行处理。

## 写什么

- 写项目特有约定、影响正确性的约束和容易误判的例外。规则说明适用条件和预期行动，需要时就近补充原因。
- 面向后续新增和修改写规则，说明项目已确定的做法与有效例外。本次变更记录和当前实现介绍不能代替规则；暂定方案、尚未实现或未验证的要求明确标注边界。
- 区分必须满足的约束、推荐默认值和可选方案；强制要求应有可检查的结果，未确认的团队政策列为待决，不将猜测写成强制规则。
- 命名与目录仅记录实际约定。参考代码应指向现存文件，并说明借鉴哪一部分，避免把整个示例的偶然细节视为规则。
- 容易被误改的行为连同原因和适用边界一起记录。只在多步操作确有遗漏风险时增加检查清单。
- 配置和脚本是可执行事实的依据。文档记录入口及不易推断的前提，避免重复抄写容易变化的配置。
- 当前代码、配置和测试用于核对实现及证据范围，不自动成为正确规则；暂定接口和未实现目标不写成已确认契约或已完成能力。

## 放哪里

- 每次开发都需要的简短约定放在 AGENTS.md；特定任务才需要的完整要求按任务组织到分册，复用已有合理位置，不要求每模块一份文档。
- 每项具体规则明确唯一维护位置，其他位置通过链接引用。入口可保留必要摘要，摘要与细则保持一致；日志、SQL、测试等详细规则由对应规范维护。
- 分册入口写明链接和具体触发条件，例如“修改数据库迁移文件前读取”；路径相对所在文档解析。
- 通用入口使用显式读取要求和链接，不自动展开全部分册。工具专用入口保留工具独有内容并连接统一入口，通用规则只维护一份；避免自动导入或递归展开形成循环，普通文档允许按需交叉引用。

## 怎么维护

1. 确定当前范围，盘点已有规则、摘要和引用；逐项区分长期要求、当前实现、暂定方案、实现缺口与历史记录，保留迁移后对照依据，不要求额外建立固定格式的台账。
2. 结合已确认决策、代码、配置和测试核对事实及验证边界，优先更新已有权威位置。按读取场景决定内联或分册，提炼条件、行动、例外和验证方式，不整段复制阶段记录。
3. 对实现与规则的差异明确标注，按当前任务范围处理。依据已确认约定修正遗漏和过时描述；确实需要新决策时再澄清，不擅自以当前代码或旧文档决定正确规则。
4. 新建、移动、合并或删除规范时，同步更新统一入口、必要摘要、触发条件、项目发现入口及其他引用；原开发文档按上述生命周期要求处理。
5. 对照盘点检查有效规则有无遗漏、重复维护、命令漂移、过时路径或触发条件缺失。检查摘要、一般规则与例外是否冲突，按已确认约定明确适用边界及优先关系。

## 怎么验收

- 结构检查：核对相对链接与锚点、代码及测试入口、实际命令和运行前提，清理空章节、失效说明与占位符，检查工具入口自动导入无循环。
- 内容审查：逐项对照原有有效规则，检查提炼后的含义、状态与证据边界。例如，项目要求失败保留草稿时，还需核对认证失效或权限撤销等例外，明确一般规则的适用范围。
- 自包含审查：在阅读范围中排除阶段性开发文档，确认长期规范正文及其必读引用仍能指导工作；同时检查“按此前方案”等隐含依赖，无须实际删除文件。
- 任务走查：从统一入口选取修改代码、修改规范及受影响分册的代表性任务，确认能找到规则、实际实现位置和验证要求。
- 按改动风险执行项目适用检查，不为文档整理新增空测试。分别报告结构与内容审查、实际行为及未验证范围；链接有效不代表语义正确或运行能力已接通。

规范随相关实现更新。再次执行时只补实际差异，已有有效内容不重复创建或追加同义规则。
