# 工程基础搭建

按团队要求沉淀项目长期规范并搭建适用的基础能力，由目标工程的语言、框架和环境决定具体实现。规范和必要实现均为正式产出，交付时说明各自的验收结果。

## 识别目标工程

使用用户指定的工程目录；未指定时使用当前工作目录。区分目标工程与本 skill 的资源目录，所有工程产出写入目标工程。

读取适用的项目指令，检查目录、依赖配置、已有规范和工作区状态，确定：

- 项目用途及当前任务需要搭建的能力。
- 已有技术栈、启动和检查入口、运行环境。
- 已实现的能力、需要补齐的部分和有效的团队约定。

从会话和工程中获取已有信息，仅澄清会影响当前实施的缺失决策。空工程可以先建立技术栈无关的规范；为尚未用到的模块预选框架不是前提。

## 统一交付要求

每个选中且适用的模块均遵循以下交付要求。分册只补充模块特有的决策和验收，已有内容满足要求时复用，不要求每个模块新建文件：

- 项目长期规范：明确后续新增或修改相关能力时应遵循的规则、适用条件、项目选择及有效例外。结合技术栈和已有约定适配，不能仅以本次变更记录或当前实现介绍代替规则，也不直接复制整份 skill。
- 必要实现：按当前需求补齐代码、配置、脚本或工具入口。实现已经符合要求时，可以只补规范；尚无业务或运行场景时，可以先沉淀已确定规则，明确尚未实现及待验证部分，不为展示规范制造业务代码。
- 发现入口：规范复用项目已有文档位置，接入 README、开发文档或规范目录等实际入口。已有 AGENTS.md 或其他 Agent 入口时，同步带触发条件的规范索引；单独执行功能模块不要求接入完整 AI 协作模块。
- 验证结果：分别说明规范与入口的检查、实现行为验证，以及缺项和外部条件限制。

目标工程内的长期规范应足以指导后续开发者或 Agent 完成相关修改，不依赖再次加载本 skill，也不直接或间接依赖可能归档或删除的阶段性开发文档。跨模块规则维护一份，配置和脚本可直接表达的事实由文档链接其来源；仅有简短约定时内联，不固定为每模块一份分册。

工程产出及其必要依赖保存在目标工程或由项目依赖机制提供，不依赖本 skill 的安装路径。

## 实施与适配

- 遵守选中模块的必须要求，按适用条件采用推荐默认值和可选项。复用目标工程现有能力，避免增加职责重复的组件。
- 从项目配置中补全可确认的命令、路径和接入方式。确需选型时依据技术栈和需求选择成熟方案，不把旧工程示例当作唯一实现。
- 已有文件采用局部补充或调整，保留有效约定与人工内容。能够依据已确认约定解决的冲突直接修正；需要新决策时澄清，并继续处理不依赖该决策的部分。
- 按模块指引使用资源，仅生成确有内容的文件；当前实现与已确定规则的差异按本次范围补齐，其余明确记录。
- 重复执行时补齐实际差异；已满足要求的内容保持不变。

代码仓库不执行部署或回滚，构建交付模块只提供产物与外部部署交接。真实推送和通知按用户授权范围执行，搭建模板本身不触发外部操作。

## 验收与交付

按本次修改范围和风险执行模块验收。新增能力验证关键成功、失败及资源边界；已有能力局部调整时重验受影响部分。专项检查以工程确有该机制且本次涉及其接入或修改为前提，不为覆盖场景增加原本不需要的设施。

多个模块同时接入时，选取代表性实际链路，验证接口、状态、失败传播与资源处理一致，并核对配置、命令及适用 CI 门槛。具体断言由分册维护，可用同一次链路验收各模块的不同结果。

验证证据应对应最终输入及产物；收尾后仍有修改时，按 [测试模块的证据更新规则](references/testing.md#构建冒烟重试与结果) 重跑受影响检查。分别说明本地、CI 与外部平台的验证范围。

逐个适用模块补查统一交付要求：

- 从项目实际入口能找到适用规范，链接有效，规则与实际文件、命令及有效例外一致。
- 为每个模块选一个代表性的后续新增或修改场景，只依据项目内规范及其链接的代码、配置或脚本，核对能否确定应读规则、允许的做法及验证入口；缺少信息时补齐对应规范或索引。此次走查不要求实际新增业务，也不等同于后续 Agent 已实际遵守规范。
- 规范完整性与实现行为分别验收。仅文档落地时不宣称运行能力已接通，仅实现通过时不宣称长期规范已交付。

最终说明：

- 完成的模块、长期规范及其发现入口、必要实现与关键选择，注明复用或新增的内容。
- 实际执行的检查与结果。
- 未覆盖、未完成或因外部环境而未验证的部分及原因。

区分已生成、已验证和仍有缺项，不将文件存在或未接入模块描述为能力已完成。

## 维护本 Skill

新增模块或调整 skill 组织时读取 [设计文档](DESIGN.md) 中的模块结构与接入步骤。为目标工程执行搭建时，无须读取设计记录或将其中的候选项当作正式要求。
