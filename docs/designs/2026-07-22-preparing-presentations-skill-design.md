# Preparing Presentations Skill 设计

> 状态：已确认，待实现。

## 1．背景

本设计来自一次完整的 Agent 技术分享准备实践。该实践最终形成了分享简报、总大纲、分章讨论记录、研究材料、完整讲稿、时间版本、PPT 故事板、素材清单、演示手册、Q&A 题库和正式 PPTX。

复盘表明，最有价值的部分不是单次生成 PPT，而是将一个内容较多、边界尚不清晰的分享主题逐步收敛为可讲、可控、可交付的演示。关键路径是：

```text
目标与听众
→ 核心命题与内容取舍
→ 分段研究、讨论和确认
→ 完整讲稿
→ 时间压缩
→ 逐页故事板
→ 素材与演示 Gate
→ 最终演示产物
→ 排练与交付
```

本次将该流程封装为可复用 Skill，供后续演讲与分享准备使用。

### 2.3 目标场景

面向以知识、观点和经验传播为主要目标的演讲与分享，包括但不限于：

- 技术分享；
- 经验分享；
- 培训课程；
- 主题演讲。

Skill 支持从模糊主题开始完整陪跑，也支持在用户已经具备大纲、讲稿、故事板或 PPT 时从中间阶段接入。

### 2.4 非目标

第一版不覆盖以下以决策、审批或工作汇报为主要目标的场景：

- 项目进展汇报；
- 方案评审；
- 述职汇报；
- 销售提案和融资路演。

第一版也不实现新的 PPT 生成引擎。需要生成或编辑 PPTX 时，调用已有的 `presentations` Skill；需要网页演示时，调用相应的网页构建能力。

## 3．设计原则

### 3.1 先设计表达，再制作载体

PPT、网页或提词卡是最终载体，不是内容思考的起点。关键内容尚未确认时，不直接进入视觉制作。

### 3.2 按输入成熟度接入

Skill 首先盘点用户已有内容，判断从哪个阶段开始，不要求已有成熟产物的用户重复走完整流程。

### 3.3 按复杂度裁剪产物

Skill 只创建完成当前分享所需的最小文档集合，不机械生成完整目录。

### 3.4 分段讨论，逐步冻结

长分享按章节推进。每章经历“讨论中／待确认／已冻结”三个状态，未经用户明确确认的内容不能进入最终讲稿。

### 3.5 文件是协作事实来源

阶段结论及时写入文档。后续工作优先读取文件，而不是依赖长对话记忆。

### 3.6 保留分享者的表达风格

Agent 负责组织、质疑、补证、压缩和打磨，不将所有讲稿改写成统一的模板化表达。

### 3.7 手工接管后不自动覆盖

用户开始手工编辑最终 PPTX、网页或讲稿后，该文件成为新的事实来源。除非用户明确确认，不得通过重新生成覆盖手工修改。

## 4．自适应工作流

### 阶段 0：入口判断

盘点用户已有的主题、材料、大纲、讲稿、故事板、图片、现场演示和最终演示文件，并判断当前成熟度。

可能的接入点包括：

- 只有模糊主题：从分享简报开始；
- 已有内容清单：从叙事设计开始；
- 已有成熟大纲：从分段共创或完整讲稿开始；
- 已有完整讲稿：从故事板或时间压缩开始；
- 已有 PPT：从审阅、补充备注或排练开始。

### 阶段 1：分享简报

确认以下内容：

- 表达目标；
- 听众画像和已有认知；
- 使用场景；
- 时间边界；
- 希望听众最终理解、相信或能够做到什么；
- 明确不讲什么。

### 阶段 2：叙事设计

形成核心命题、叙事主线、内容优先级、章节结构和时间预算。对于候选内容过多的情况，主动给出删除、合并或降级建议。

### 阶段 3：分段共创

逐章讨论、研究和取舍。每章至少回答：

1. 这一段要让听众理解什么；
2. 听众凭什么相信；
3. 使用什么例子、证据或互动；
4. 如何过渡到下一段。

外部事实、个人经验、当前探索和未来设想分别标记。需要外部研究时优先使用一手来源；技术分享可按需启用代码盘点、项目文档查阅和架构分析。

### 阶段 4：完整讲稿

将已冻结章节组合成可口述讲稿，重点处理：

- 开场和收束；
- 章节过渡；
- 跨章节重复；
- 书面腔和模板化表达；
- 页面切换与现场动作；
- 时间预算。

完整讲稿不是分章文档的机械拼接。

### 阶段 5：故事板与素材

逐页或逐屏定义：

- 页面目标；
- 核心信息；
- 推荐视觉形式；
- 演讲者备注；
- 所需素材；
- 与前后页面的关系。

同时盘点素材状态，规划现场演示、切屏步骤和降级方案。

### 阶段 6：演示产物

根据用户选择生成或编辑：

- PPTX；
- 网页演示；
- 纯讲稿；
- 提词卡或其他轻量载体。

生成视觉产物前必须确认故事板和关键素材状态。需要 PPTX 时调用已有 `presentations` Skill，不在本 Skill 中复制幻灯片生成实现。

### 阶段 7：排练与交付

检查总时长、章节节奏、压缩顺序、Q&A、现场互动、演示切换和风险点。根据需要准备安全版、标准版和完整版，但不通过加快语速实现压缩。

工作流允许返回上一阶段修订，也允许用户明确跳过不需要的环节。

## 5．产物分级

### 5.1 轻量模式

适用于 15 分钟以内、主题明确且不包含复杂现场演示的分享。

建议产物：

- 分享简报；
- 大纲；
- 讲稿或提词卡。

### 5.2 标准模式

适用于 15～45 分钟、有多个章节或需要一定素材组织的分享。

在轻量模式基础上增加：

- 分章记录；
- 时间表；
- 故事板；
- 素材清单。

### 5.3 完整模式

适用于长时分享、多人协作、研究密集或包含现场演示的场景。

在标准模式基础上按需增加：

- 来源登记；
- 研究记录；
- 演示手册；
- Q&A 题库；
- 多个时长版本；
- 排练记录。

## 6．交互规则

1. 一次只推进一个关键决策，默认给出推荐方案和取舍理由。
2. 用户提供完整想法后，先提炼并记录，再讨论缺口，不要求用户重复整理。
3. 复杂分享按章节推进；未经明确确认，不将章节标记为“已冻结”。
4. 主动识别内容过多、概念过密、案例重复和时间失衡。
5. 阶段结束时更新文档和状态，再进入下一阶段。
6. 用户可主动跳过环节；Skill 说明跳过后的风险，但不强制补齐。
7. 用户要求直接生成 PPT 时，先判断是否已有足够明确的内容和故事板；信息足够则执行，信息不足则只询问阻塞性的关键问题。
8. 已存在人工修改的最终文件时，优先编辑该文件，重新生成前必须确认。

## 7．质量 Gate

### 7.1 分享简报 Gate

- 目标、听众、场景、时长是否明确；
- 听众最终带走什么是否可描述；
- 内容边界是否明确。

### 7.2 叙事 Gate

- 能否用一句话说清核心命题；
- 每章是否服务于核心命题；
- 内容优先级是否与时间匹配。

### 7.3 章节 Gate

- 是否有明确目标；
- 是否有证据、案例或互动；
- 是否形成结论；
- 是否能自然过渡。

### 7.4 时间 Gate

- 章节预算之和是否正确；
- 是否预留互动、演示和 Q&A；
- 是否有明确压缩顺序。

### 7.5 讲稿 Gate

- 是否适合口述；
- 是否存在书面腔、模板化表达和重复解释；
- 是否包含必要过渡和现场动作。

### 7.6 故事板 Gate

- 每页是否只有一个主要任务；
- 视觉是否帮助表达而非装饰；
- 页面与讲稿是否一致。

### 7.7 素材和演示 Gate

- 关键素材是否就绪并可使用；
- 现场演示是否有操作步骤；
- 高风险演示是否有降级方案。

### 7.8 最终交付 Gate

- 页面、备注、讲稿和故事板是否一致；
- 最终文件是否完成视觉检查；
- 是否尊重用户手工修改后的事实来源。

## 8．Skill 包结构

第一版采用“流程＋契约”结构：

```text
preparing-presentations/
├── SKILL.md
├── agents/
│   └── openai.yaml
└── references/
    ├── artifact-contracts.md
    ├── facilitation-playbook.md
    └── quality-gates.md
```

- `SKILL.md`：触发条件、入口判断、核心工作流和资源路由；
- `artifact-contracts.md`：各类产物的职责、最小字段和适用模式；
- `facilitation-playbook.md`：逐步提问、分章确认、内容取舍和手工接管规则；
- `quality-gates.md`：阶段检查表和完成标准；
- `agents/openai.yaml`：Codex Skill 展示信息和默认提示。

第一版不增加 README、模板资产和复杂校验脚本。经过数次真实使用后，再判断哪些文档模板或检查规则值得自动化。

## 9．验证方案

Skill 采用场景测试验证，不以目录创建成功作为完成标准。

### 场景一：模糊主题的长技术分享

输入只有大致主题和若干想法。验证 Skill 是否先确认目标、听众和时间，再建立分章讨论流程，而不是直接生成 PPT。

### 场景二：已有成熟大纲的培训课程

验证 Skill 是否从讲稿或故事板阶段接入，不要求用户重新回答已经明确的问题。

### 场景三：10 分钟经验分享

验证 Skill 是否选择轻量模式，避免创建完整研究、演示和 Q&A 文档体系。

### 场景四：关键上下文缺失

用户未说明听众或时长。验证 Skill 是否一次只询问一个真正阻塞的关键问题。

### 场景五：要求直接生成 PPT

验证 Skill 是否判断现有输入是否足够；信息足够时直接推进，信息不足时不假装完成内容设计。

### 场景六：人工修改后的 PPT

验证 Skill 是否将现有 PPT 视为事实来源，并避免重新生成覆盖用户修改。

实施时先记录未加载 Skill 的基线表现，再加载 Skill 执行相同场景，最后针对暴露的歧义进行修订。

## 10．完成标准

第一版完成需要满足：

1. Skill 目录由官方初始化脚本创建；
2. `SKILL.md` 和三份参考文档完成；
3. `agents/openai.yaml` 与 Skill 内容一致；
4. 通过 Skill 结构校验；
5. 六类场景至少覆盖代表性测试；
6. 不包含本次 Agent 技术分享的主题专属内容；
7. 尚未安装到个人 Skill 目录。
