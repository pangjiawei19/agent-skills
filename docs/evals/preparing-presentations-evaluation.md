# Preparing Presentations Skill 场景评估

## 评估目的

使用相同压力场景对比未加载 Skill 与加载 Skill 后的行为，验证 Skill 是否真正改变演讲准备流程，而不只是在仓库中增加文档。

## 评分规则

每个场景按以下六项评分，每项 `0` 或 `1`，总分为 `6`：

1. 正确识别已有内容成熟度和接入阶段；
2. 只询问一个当前最关键的问题，或在信息充分时直接推进；
3. 选择最小必要产物模式；
4. 不在内容未确认时贸然生成最终载体；
5. 明确阶段产物和确认 Gate；
6. 尊重既有人工修改，不提出无确认覆盖。

硬失败条件：

- 对模糊主题直接生成完整 PPT；
- 要求已有成熟大纲的用户重新从零回答全部问题；
- 为 10 分钟分享创建完整研究、Q&A 和演示体系；
- 未经确认覆盖用户已经手工修改的 PPT。

## 压力场景

### Case A：模糊主题＋缺少关键信息＋要求直接做 PPT

> 我下个月想做一次关于 AI 如何改变研发工作的分享，手上有很多零散想法。你先直接帮我生成一份完整 PPT，细节你看着办。

### Case B：已有成熟大纲的培训课程

> 我要给新员工做一场 30 分钟的代码评审培训。我已经确定三部分：为什么要评审、如何提交可评审的改动、如何给出有效反馈；每部分各 8 分钟，开场和问答各 3 分钟。请继续帮我准备。

### Case C：10 分钟经验分享

> 我要做一次 10 分钟经验分享，主题是我如何减少会议时间。听众是同组同事，我只想讲三个真实做法，不需要现场演示。

### Case D：已有人工修改的 PPT

> 我已经在原 PPT 里手工调整了结构、配色和备注，现在想继续完善最后五页。请不要丢掉我已经改过的内容。

## RED 基线

测试方式：由独立 subagent 在不读取 Skill、设计文档或计划的条件下，仅根据场景给出下一步回复和后续动作。

### Case A 基线响应

> 我会直接开始制作，不再追问细节。先按以下默认设定推进：面向研发与技术管理者、30 分钟分享、16:9 中文演示文稿，风格专业但有观点，兼顾趋势判断、真实工作场景和可执行建议。
>
> 随后我会：
>
> 1. 将零散主题整理成“变化—案例—风险—行动”的完整叙事。
> 2. 设计约 15～18 页内容，包括标题、核心观点、图示、案例与结尾行动清单。
> 3. 生成可编辑的 PPT 文件。
> 4. 检查文字密度、版式一致性和演讲节奏，并附一份简短讲稿提示。

评分：

| 项目 | 分数 | 理由 |
|---|---:|---|
| 识别成熟度和入口 | 0 | 看到了“零散想法”，但没有据此停在分享简报或叙事设计阶段。 |
| 单个关键问题／充分时推进 | 0 | 未询问目标、听众或时长，直接替用户做出多项假设。 |
| 最小必要产物 | 0 | 未判断复杂度便决定生成 15～18 页 PPT 和讲稿提示。 |
| 不贸然生成最终载体 | 0 | 明确承诺直接生成完整 PPT。 |
| 阶段产物和确认 Gate | 0 | 没有用户确认节点。 |
| 尊重人工修改 | 1 | 本场景无既有人工修改，也未提出覆盖。 |
| **总分** | **1／6** | 触发硬失败。 |

硬失败：是。对模糊主题直接生成完整 PPT，并用未经确认的假设填补关键信息。

### Case B 基线响应

> 可以。我会按你已经确定的 30 分钟结构继续准备，并先默认受众是“有基础开发经验、刚加入团队的新员工”，内容不绑定具体语言或代码托管平台。
>
> 接下来我会产出一套可直接开讲的材料，包括：
>
> - 30 分钟逐分钟议程。
> - 每部分的讲解提纲和讲师备注。
> - “难以评审”与“易于评审”的改动示例。
> - 有效反馈与无效反馈的对照案例。
> - 适合现场互动的简短练习。
> - 一页式课后检查清单。
>
> 随后我会先完成逐分钟议程，再补齐三部分讲稿和案例，最后整理互动题与课后材料。如果你们已有特定技术栈或代码评审平台，我会再把示例替换成更贴近团队日常工作的版本。

评分：

| 项目 | 分数 | 理由 |
|---|---:|---|
| 识别成熟度和入口 | 1 | 复用了既有结构，没有要求从主题重新开始。 |
| 单个关键问题／充分时推进 | 1 | 信息足以推进，未重复询问已明确内容。 |
| 最小必要产物 | 1 | 产物与 30 分钟培训基本匹配。 |
| 不贸然生成最终载体 | 1 | 先形成议程和内容，没有直接承诺生成 PPT。 |
| 阶段产物和确认 Gate | 0 | 有阶段顺序，但没有先让用户确认议程再扩写的 Gate。 |
| 尊重人工修改 | 1 | 本场景无既有人工修改，也未提出覆盖。 |
| **总分** | **5／6** | 未触发硬失败。 |

硬失败：否。主要缺口是缺少显式确认 Gate。

### Case C 基线响应

> 可以，我会把内容严格控制在 10 分钟，只讲三个真实做法，不加入现场演示或泛泛的效率理论。
>
> 请把你的三个做法各用一两句话告诉我；不需要整理，零散描述即可。最好包含：
>
> - 以前会议哪里浪费时间；
> - 你具体改变了什么；
> - 实际产生了什么效果。
>
> 收到后，我会筛选并组织素材，形成“开场背景—三个做法—效果总结”的分享结构，再为每一部分写好页面文案和口头讲稿，并校准到 10 分钟以内。

评分：

| 项目 | 分数 | 理由 |
|---|---:|---|
| 识别成熟度和入口 | 1 | 正确识别已有主题但缺少三个真实做法的内容事实。 |
| 单个关键问题／充分时推进 | 1 | 聚焦请求用户提供三个做法，附带字段只是降低整理成本。 |
| 最小必要产物 | 1 | 只规划结构、页面文案和口头讲稿，没有扩展完整研究体系。 |
| 不贸然生成最终载体 | 1 | 先收集真实做法。 |
| 阶段产物和确认 Gate | 0 | 未说明结构形成后先确认再写完整讲稿。 |
| 尊重人工修改 | 1 | 本场景无既有人工修改，也未提出覆盖。 |
| **总分** | **5／6** | 未触发硬失败。 |

硬失败：否。轻量化合理，但仍缺显式确认 Gate。

### Case D 基线响应

> 可以。我会以你手工调整后的最新版 PPT 为唯一基线，只处理最后五页，不重建整套文件，也不会覆盖前面页面的结构、配色或备注。
>
> 请把最新版 PPT 上传，并简要说明最后五页希望重点完善什么，例如内容精简、版式统一、视觉强化或讲稿补充。
>
> 随后我会：
>
> - 先核对最后五页与现有整体风格；
> - 在副本中进行局部修改；
> - 保留现有页面元素、主题设置和演讲者备注；
> - 完成后逐页检查，并明确列出每页改动。

评分：

| 项目 | 分数 | 理由 |
|---|---:|---|
| 识别成熟度和入口 | 1 | 正确从既有 PPT 的局部完善阶段接入。 |
| 单个关键问题／充分时推进 | 1 | 上传最新版和说明最后五页目标属于同一个阻塞性材料请求。 |
| 最小必要产物 | 1 | 明确只处理最后五页。 |
| 不贸然生成最终载体 | 1 | 先读取最新版并核对风格。 |
| 阶段产物和确认 Gate | 1 | 明确限定副本、局部修改和逐页改动说明，形成可核验交付边界。 |
| 尊重人工修改 | 1 | 将人工修改后的 PPT 作为唯一基线，不重建、不覆盖。 |
| **总分** | **6／6** | 未触发硬失败。 |

硬失败：否。该场景的自然行为已经符合目标规则。

## RED 结论

- Case A 为明确硬失败，总分 `1／6`，证明缺少 Skill 时 Agent 容易把“用户允许自行决定细节”理解为可以跳过目标、听众和时长确认。
- Case B、Case C 的共同缺口是只有产出顺序，没有明确的用户确认 Gate。
- Case D 表明“尊重人工修改”有较强的自然行为基础，Skill 应将其固化为不可回退的规则，而不需要增加复杂流程。
- RED 条件成立，可以进入最小 Skill 实现。

## GREEN 复测

Skill 完成后使用相同四个场景和相同评分规则复测，完整记录响应、评分和必要的 REFACTOR。
